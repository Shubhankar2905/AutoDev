## Current Architecture

Your generated apps are created by the E2B Docker image, not by `sandbox-template/nextjs/my-app`.

The active flow is:

1. [e2b.Dockerfile](sandbox-template/nextjs/e2b.Dockerfile#L1-L20) creates a fresh Next.js app.
2. It currently uses `create-next-app@15.3.3`.
3. It initializes shadcn with `shadcn@2.6.3`.
4. It installs all shadcn components.
5. [compile_page.sh](sandbox-template/nextjs/compile_page.sh#L1-L21) starts the development server on port `3000`.
6. [src/inngest/functions.ts](src/inngest/functions.ts#L45-L48) creates sandboxes from the E2B template.
7. The coding agent writes generated files into `/home/user`.
8. The preview URL is stored in Prisma and displayed by the project UI.

There is currently version drift:

- Host application: Next.js `16.2.10`
- Docker-generated application: Next.js `15.3.3`
- Checked-in `my-app`: Next.js `16.1.4`
- Host and template use Tailwind CSS 4
- The checked-in `my-app` does not contain the shadcn components installed by the Dockerfile

The canonical source should be the Dockerfile-generated application.

## Recommended Target Strategy

Do not use unbounded `latest` values in production. The safer approach is:

1. Check the current stable versions.
2. Select compatible versions.
3. Pin those versions explicitly.
4. Rebuild and publish the E2B template.
5. Test the generated app.
6. Update the agent instructions to match the actual generated filesystem.

A practical target would be:

- Supported Node.js LTS version
- Latest compatible Next.js version
- Matching React and React DOM versions
- Latest compatible Tailwind CSS 4
- Current shadcn CLI
- Current shadcn `new-york` style
- Lucide icons
- Radix dependencies generated by shadcn
- TypeScript and ESLint versions compatible with the selected Next.js release

The exact versions should be selected together. Next.js, React, Node.js, Tailwind, and shadcn CLI should not be upgraded independently without rebuilding and testing the template.

## Implementation Plan

### Phase 1: Choose the canonical template

Decide that the Dockerfile-generated project is the source of truth.

The checked-in `my-app` should either:

- Be regenerated to match the Dockerfile, or
- Be clearly treated as an unused reference project.

Do not update only `my-app/package.json`; that would not change the apps created by E2B.

### Phase 2: Upgrade the E2B scaffold

The Dockerfile would need to:

1. Use a supported Node.js LTS image.
2. Use the selected current `create-next-app` version.
3. Use the selected current shadcn CLI version.
4. Verify the current CLI syntax for:
   - `shadcn init`
   - `shadcn add --all`
5. Confirm that the generated app contains:
   - `components.json`
   - `components/ui`
   - `lib/utils`
   - Correct TypeScript aliases
   - Tailwind 4 configuration
   - Lucide and required Radix dependencies

The shadcn CLI changes over time, so the command syntax should be tested in a temporary Docker build before publishing.

### Phase 3: Align the agent prompt

[src/prompt.ts](src/prompt.ts#L30-L45) must be updated so its assumptions match the rebuilt template.

The prompt should describe:

- The selected Next.js version
- The selected React version
- The actual working directory
- The actual shadcn component paths
- The actual Tailwind setup
- The current `components.json` configuration
- The correct client/server component rules
- The correct package installation process

Important prompt changes would also be needed for these conflicts:

- It currently says Next.js `15.3.3`.
- It says all shadcn components are available without verifying them.
- It forbids all CSS changes, although shadcn theme configuration may require `globals.css`.
- It says `page.tsx` should always use `"use client"`, which unnecessarily disables server components.
- It forbids image URLs, which may unnecessarily restrict valid local assets.
- It assumes the server always runs on port `3000`.

The generated app should use `"use client"` only when hooks, browser APIs, or client event handlers are needed.

### Phase 4: Verify runtime behavior

After rebuilding the E2B template, verify:

1. The container starts successfully.
2. `/home/user` is the active project directory.
3. `http://localhost:3000` returns successfully.
4. Hot reload works after file changes.
5. `@/components/ui/button` and other shadcn imports compile.
6. `@/lib/utils` exists and works.
7. Tailwind classes compile.
8. The generated app builds without missing dependencies.
9. The preview URL from `getHost(3000)` remains valid.
10. The agent can install additional packages with npm.

### Phase 5: Publish and connect the template

[e2b.toml](sandbox-template/nextjs/e2b.toml#L14-L17) identifies the published template.

After rebuilding:

- Publish a new E2B template.
- Prefer a versioned template name or tag.
- Update the template name used by `Sandbox.create(...)` in [src/inngest/functions.ts](src/inngest/functions.ts#L45-L48).
- Redeploy the Inngest worker/application.
- Test a new project from the UI.

Changing the template does not update existing sandboxes or previously generated projects.

## Important Existing Limitation

Every generation request currently creates a new sandbox.

That means follow-up prompts do not continue modifying the original running app. The previous messages are loaded, but the previous filesystem is not restored into the new sandbox.

For reliable follow-up editing, you would eventually need to either:

- Persist and restore the generated files into every new sandbox, or
- Persist the E2B sandbox ID and reconnect to the existing sandbox.

That is separate from the Next.js/shadcn upgrade, but it affects testing and user expectations.

## Recommended Order

1. Select compatible Node, Next.js, React, Tailwind, and shadcn versions.
2. Update and test the Docker-generated scaffold.
3. Build and inspect the resulting E2B filesystem.
4. Align [src/prompt.ts](src/prompt.ts#L30-L45) with the real filesystem.
5. Publish a versioned E2B template.
6. Point [src/inngest/functions.ts](src/inngest/functions.ts#L45-L48) to it.
7. Test first generation.
8. Test dependency installation and shadcn imports.
9. Test preview loading and hot reload.
10. Separately address sandbox persistence for follow-up prompts.
